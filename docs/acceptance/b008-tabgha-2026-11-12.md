# B-008 reproduction on Tabgha, 12 November 2026

Evidence for [B-008](../BACKLOG.md#b-008) step B-008-T01: the dashboard on Tabgha while a chat is relayed to Neo Tokyo-3, on current main.

**Who ran it:** the agent, over SSH from Neo Tokyo-3, with the owner's approval (2026-11-12) to update Tabgha. The dashboard was the real one, in headless Microsoft Edge on Tabgha, signed in through `open dashboard --print`; the chat went through the page's own `window.chat`, so it took the same path as typing in the dashboard chat.

**Machines and revisions:** Tabgha (`NERV-02`, Windows 10.0.26200, Node v24.22.2), updated from `b68802d` to `8c58ee5` (stopped through `service stop`, database copied, `git pull --ff-only`, `npm ci --ignore-scripts`, `npm run build`, `service start`). Neo Tokyo-3 (`NERV-01`, the main base) on `f8b8116`, Misato on `gemma4:12b` (local Ollama).

**Method:** each run restarted Tabgha's service, so the chat landed in its first minute (the original report came two minutes after a start), opened the dashboard, sent the chat 20 s later and recorded every banner change plus every `/api/` request that failed, returned 400 or more, or took over 1.5 s (Chrome DevTools protocol network events), until 30 s after the reply.

The prompts were *What is the weather like in a typical spring, in three short paragraphs?* and a longer five-paragraph request. The only request open at the end of each run was the live `GET /api/dashboard/stream`. Tabgha's `service-error.log` holds only Kaji link lines for these runs.

**Conclusion:** on current main, a relay of 47 s and one of 210 s (the original was about 80 s) left the banner live with no failed or slow dashboard read. The original timeout (*Request timed out; outcome may be unknown.*, a pre-#153 ProcessClient IPC timeout) did not reproduce; its cause stays unidentified.
