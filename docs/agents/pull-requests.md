# Pull requests

Read before you open, update or merge a PR. The never and ask-first rules stay in AGENTS.md (its safety block); this page holds the workflow.

## Opening and updating a PR

Open every PR against `main`, never on another PR's branch (merging it would not reach `main`). When a PR addresses a backlog item, include its ID in the title (`feat(<ID>): <summary>` or `fix(<ID>): <summary>`). Sign the PR body with the agent that produced it (for example, `🤖 Generated with Claude Code` or `🤖 Generated with Antigravity`). With source-owned records, open it with `npm run work:pr -- <ID>[,<ID>] -- <gh pr create options>` from a clean work branch: it writes the PR's number into each record before the PR exists (the next number GitHub will assign; it refuses a branch that already has an open PR), commits, pushes and opens the PR, so no follow-up commit names it; if another issue or PR took that number meanwhile it renames it in a follow-up commit and says so. Its commits end with the project's attribution lines: `--trailer="Key: value"` before the `--` (repeatable) or `HARNESS_COMMIT_TRAILER` (one per line), else the `Co-Authored-By` trailers of the branch's newest commit. Once a PR's CI is green the owner may merge it at any moment: push no new work to it, open a new PR. Exception: a green PR that conflicts with `main` cannot merge, so it may get a push that only resolves the conflict; its checks run again before it can merge. A conflict in `docs/BACKLOG.md` is resolved record by record, never by keeping one side's record (that silently drops the other side's edits): with source-owned records (`workItems.enabled`) resolve the record and task sources, preserving both sides, then regenerate the views (`npm run work:build`); otherwise use `node tools/merge-backlog.mjs`. With `workItems.views: "built"` (F-096) the ledger is a build output, ignored by git and never committed, so no PR conflicts on it: `npm run work:build` writes it locally and `work-items check` and the other ledger readers build it fresh before reading it, and `merge-backlog.mjs` is left for hand-written ledgers (projects without `workItems`). CI attaches it to each run as the `backlog-views` artifact, and on `main` the copied `backlog-views.yml` workflow builds it in a read-only job, runs the project's `workItems.publishHooks` there (F-100), and publishes it from a second job with `work-items publish --ledger` on the `backlog-views` branch (the commit's tree plus the ledger, so `blob/backlog-views/docs/BACKLOG.md#f-005` and its record links resolve).

## Checks

- With scoped verification explicitly enabled, follow [verification selection](verification.md): applicable fast checks and affected regressions by default; full deterministic checks on request, risk or freshness limits. Without adoption, the checks in AGENTS.md ("Checks before you finish") remain required. Run the fast local checks (format, lint, typecheck, backlog, rules, maintenance) in one pass before pushing to avoid multi-push CI cycles.


## Independent review

- **Independent review.** A PR that closes a P1 record or changes a harness file (a file listed in `.harness.json`, or the template itself) gets a review in a fresh context before it merges: a review skill or a separate session that did not write the change reads the diff and the record's Check for bugs, security and compliance. It also reads for changes outside the record's scope, complexity nobody asked for (options, one-use abstractions, handling for cases that cannot occur) and code that does not follow its neighbours' patterns. Its findings are fixed in the PR or answered there. The record cites it: `Review: <how, outcome>`. Documentation-only and small (a few lines, no behaviour) changes are exempt; a P1 record says why: `No review: <reason>`. So is a reconcile whose only harness-file changes are byte-identical copies of `copied` files from a published template tag, their `copied` entries and the `version` stamp, when `node tools/check-harness.mjs --strict` passes on the PR head (it exits 1 if any copied file differs or the template is missing); the record cites it as `No review: check-harness --strict matched vX.Y.Z`. Any adapted file (AGENTS.md and BACKLOG-RULES included), forked or project-written change, or a P1 closure in the same PR still needs a reviewer. Match the reviewer to the change: mechanical checks (byte copies, version bumps, a reformat whose syntax tree is unchanged, regenerated views) can run on a smaller, cheaper model with an explicit list of what to verify; design, safety rules, security, data migration and lifecycle code get the strongest available model. The checks required do not change with the model. In Claude Code the copied agent definitions pin the model: `mechanical-reviewer` (Haiku) and `design-reviewer` (Opus), both instructed to report and never edit or merge; other clients follow the rule through their own settings, and the work-usage ledger records which model actually ran. Pass the reviewer `git diff origin/main...HEAD` and the changed file list rather than asking it to rediscover the diff. The reviewer reports; it never approves or merges. `check:backlog` warns when a branch makes a P1 record Verified or Closed with neither; `check:freshness` reminds a branch that changes harness files.
