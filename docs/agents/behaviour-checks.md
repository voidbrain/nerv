# Behaviour checks

Read before you run the agent-behaviour checks or measure a rule change with them. Moved from [rule review](rule-review.md) (F-102).

Tools check records and files; `tools/behaviour.mjs` checks whether an agent following this project's AGENTS.md and BACKLOG-RULES behaves as they say. Each scenario builds a fixture repository from the project's own rule files (`behaviour.rules` maps fixture paths to sources), gives the agent one task and grades the result without a model: files, records, commits, the remote and the transcript. `node tools/behaviour.mjs list` names the scenarios and the rule each one tests.

The runner is the project's choice, set in `.harness.json` `behaviour.runner`: a shell command run in the fixture repository with the task in `$HARNESS_TASK_FILE`, whose output is the transcript, so it should print the agent's final reply rather than tool logs (for example `claude -p --permission-mode acceptEdits --allowedTools "Bash(git:*)" "Bash(npm:*)" "Bash(node:*)" -- "$(cat "$HARNESS_TASK_FILE")"`: in non-interactive mode the agent needs these permissions to edit files and run git, npm and node in the throwaway fixture, or it only describes what it would do). The fixture lives in a temporary folder with a local bare remote; give the runner no credentials or network access it does not need. `run` starts the runner without GitHub tokens, a gh login, SSH agent or system and global git config (credential helpers), and limits git to the file protocol, so only the fixture's local remote is reachable. `npm run behaviour -- run` runs each scenario `behaviour.times` times (3 by default) and reports passes per scenario, never only a total; `--scenarios=a,b` narrows it and `--keep` leaves the fixtures for inspection. A runner that fails to start, exits non-zero or times out (`behaviour.timeoutMs`, 20 minutes by default; its whole process group is stopped) counts as a failed run, never as a graded one. A run that changed nothing (files, refs, worktrees or the remote) where a correct run must act, or whose transcript asks for permissions instead of acting, is reported as `error (runner lacks permissions?)`: counted apart, never as a pass or a rule failure; give the runner the permissions above and run again. The graders read the agent's work wherever it put it, as AGENTS.md asks: the primary checkout, each other worktree (one nested in the checkout, such as `.claude/worktrees/<name>`, is its own view, not a change to the checkout), and each new or moved local or pushed branch; when several of them changed, each is graded and every one must pass.

**Before and after a rule change** (F-102-T07): `npm run behaviour -- run --rules-ref=<ref>` runs each scenario `behaviour.times` times on fixtures built from the rule files at that git ref (a branch, tag or commit; usually `origin/main` while the change is uncommitted or on its branch) and as many times on fixtures from the working tree, and reports both per scenario: `pass 3/3 <scenario>: <rule>; before FAIL 1/3 at origin/main`, with `dropped from n/m` when the after side passes less often. The exit code follows the after side only. The `behaviour.rules` mapping, runner and settings come from the working tree's `.harness.json` for both sides; a mapped file missing at the ref is left out of its fixture, as a missing file is today. Every run, with or without a ref, appends one line of per-scenario counts (passes, errors, runs, and the before counts with the ref and its commit) to `.harness/behaviour.jsonl` in the primary checkout: local, git-ignored, no transcripts, failure text, runner command or identity. A symlinked log is refused before any agent runs; a damaged line is skipped. The report names each scenario's last earlier run from it (`last 2/3`).

**Held-out scenarios** (F-102-T08): `behaviour.heldOut` in `.harness.json` lists scenarios kept apart from rule drafting, so a change is judged on tasks it was not tuned to (`list` marks them). While drafting or tuning a rule, run `--set=drafting` (every scenario but the held-out ones), and do not edit or tune the rule against the held-out scenarios or their graders. The change reports before and after on them with `--rules-ref=<ref>` (`--set=held-out` runs only them). A held-out scenario that passes less often after than before reads `held-out regression, a backlog record`: it becomes a B- record with the report as evidence, whatever the other scenarios show. A held-out scenario that a rule change has to edit (its fixture, task or grader) leaves `behaviour.heldOut` in that change, which says so: once tuned to, it no longer judges.

Run it on demand and when the rule files it copies change (AGENTS.md, CLAUDE.md, BACKLOG-RULES: an impact-map row), never on every PR by default: each run costs agent time. Measure a rule change with `--rules-ref`, and compare each scenario with its last run (the report names it). A scenario that starts failing is a backlog record, with the report as evidence. A drop seen in one run may be noise: that record's first step reruns the scenario with a larger `--times` (10, say) before any rule or grader changes. A mistake seen in real work or an audit finding becomes a new scenario: a fixture, a task and a grader that reads the result. A pass shows the agent followed the rule in that fixture, not in every situation.
