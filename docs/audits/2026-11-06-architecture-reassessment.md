# Architecture reassessment — 2026-11-06

Dated addendum to the [brainstorm retirement review](2026-11-06-brainstorm-retirement.md), at main `cf77cabf38b5656a5170ff9d69c80e23b39ccd92`. Scoped documentation and backlog review, with source inspection of policy, grants, runtime orchestration and model routing. This is an architectural judgement, not a full product/security audit or an instruction to implement the proposals below. Published reports stay unchanged under the [audit procedure](../agents/audit.md).

“Superseded” establishes which decision is current; it does not establish that it is better. The current [Architecture](../ARCHITECTURE.md) also contains targets. The [vocabulary diagram](../NERV-ARCHITECTURE.md) is explicitly historical. The comparison below separates delivered boundaries from desirable designs.

My overall preference is the current direction: authority checked for each action, explicit routes and independent machine/model/role concepts. Its biggest costs are more protocol machinery and lore to learn. Some replacements are only renamings, and some claimed improvements are still plans. Three-model voting was weaker as an authorization mechanism, but independent model critique remains useful advice. Replacing a mandatory sandbox product with a portable sandbox design is sensible; running without the sandbox while it remains unfinished is weaker isolation than the original target.

## Corrections to the earlier assessment

- **Sync is still partly model confidence.** [policy.ts](../../src/policy.ts) multiplies configured effect and stage factors and, when supplied for an approving Casper verdict, Casper's reported confidence. A configured stage is not empirical pilot performance. Showing inputs improves inspectability; changing 0–10 to 0–100 does not calibrate a probability. Deterministic vetoes and mandatory owner decisions remain separate gates. The earlier “not model self-confidence” wording was incorrect.
- **Spear does not perform compensation.** [Ledger.spear](../../src/ledger.ts) revokes unused grants, stands down pending approvals, marks an open sortie revoked and reports used grants with optional inverse names. [Runtime](../../src/runtime.ts) delegates this call; it does not execute those inverses. Revocation does not prove that an already-running external operation stopped. The earlier “declared inverses” wording overstated implemented behavior.
- **No silent local/cloud route fallback is narrower than no substitution.** [model.ts](../../src/model.ts) explicitly chooses the route, but its cloud request enables same-provider server-side fallback. This preserves the local/cloud privacy boundary while permitting provider-side model substitution. Reproducibility and accounting must record the actual returned model.
- **Inventory correction:** the original manifest/table contains 26 entries: 25 substantive files and one tracked `.DS_Store` metadata file. `.DS_Store` is not reference artwork; the earlier “ignored” description and artwork disposition were erroneous. This review adds no visual/OCR claims and deletes no files.

## Preserved proposals: my recommendation

These are opinions and suggested decision criteria, not new accepted closure requirements for the linked features. They do not authorize installing services, changing policy or expanding autonomy.

### 1. Backups and recovery: highest reliability value

**Recommend accepting a recovery outcome before choosing Litestream.** With durable reminders, memory and enrollment state, loss of one disk can erase operational history. Start by agreeing acceptable data loss and restore time, then implement consistent snapshots, retained encrypted off-host copies and a restore drill. Keep backup encryption/recovery keys separate from routine runtime authority; test restoring identities, revoked grants and notification checkpoints without replaying old work.

A scheduled snapshot is simpler than continuous replication and may meet personal-use needs. Litestream is interesting when the acceptable loss window is smaller; it adds storage credentials, monitoring and operational dependencies. Replication alone can copy a damaging deletion and is not failover. Retention and tested restore matter more than the tool name. [SQLite's backup API](https://sqlite.org/backup.html) supports consistent live snapshots; [Litestream's documentation](https://litestream.io/getting-started/) describes continuous replication and restoration. Neither establishes that NERV currently does this.

**Effort/risk:** medium for a bounded backup/restore path; higher for unattended replication and key recovery. **Suggested success:** recover a disposable installation on another location within the agreed loss/time bounds, without duplicate external effects or secrets in logs. Related F-002; remains proposed here.

### 2. Token and cost accounting: useful before expanding paid cloud use

**Recommend measured per-call usage and route/model attribution.** Record provider-reported input/output tokens where available, actual returned model, route, duration, outcome and usage source. Distinguish measured, estimated and unavailable values; do not record prompts or credentials merely to count usage. Show aggregate spend with price provenance and visible uncertainty. A timeout may leave provider usage unknown, so a pre-call limit and later reconciliation are distinct controls.

The current policy checks declared action cost against a sortie budget; [Ledger.propose](../../src/ledger.ts) defaults omitted cost to zero. That is not provider-token accounting. F-019 already owns cost accounting; this review does not silently add all telemetry to its acceptance.

**Context occupancy: useful diagnostic, lower priority.** Prefer “estimated input / configured context limit” to an authoritative remaining-capacity gauge. Provider tokenization, hidden overhead, cached tokens and compaction can make a single percentage misleading. For local models, count what the runtime can actually observe. Do not use occupancy as an authorization signal.

**Effort/risk:** medium across providers, persistence and pricing; low for a carefully labelled single-provider diagnostic. **Suggested success:** a known test call reconciles usage and actual model, unavailable values stay unknown, and no cloud cost is silently displayed as zero. Context counters remain a proposal beyond existing accepted accounting scope.

### 3. Automatic incident response: bounded circuits before a global kill switch

**Recommend a narrow design, defer blanket automatic revocation.** Useful first responses are deterministic: stop accepting new work for the affected scope, revoke unused grants, preserve evidence and alert the owner. Define exactly which event triggers which response, who can rearm it and what happens while disconnected. Treat model suspicion as a signal for review, not unilateral authority to stop every base.

Global cancellation creates denial-of-service and availability risks, while a physical operation may continue despite a revoked grant. Automatic “undo” can itself cause harm. Manual Spear provides a starting primitive, not a complete detector, interruption mechanism or compensation system. The [OWASP prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) supports least privilege and human oversight as layered defenses; it does not validate a NERV incident policy.

**Effort/risk:** medium for one bounded circuit, large for a cross-base incident coordinator. **Suggested success:** injected faults revoke only the intended pending authority, preserve recovery access, produce one deduplicated alert and require explicit rearm; benign inputs do not trigger a global outage. Related F-023; automatic response remains unaccepted.
