**Next action / closure evidence:** 2026-11-25, likely cause (B-126-T03, [PR #767](https://github.com/voidbrain/nerv/pull/767)): #757's watch named the step on Windows [run 45670901865](https://github.com/voidbrain/nerv/actions/runs/45670901865) (PR #761, `orchestration-selection.test.ts:506`): `still in start-up step "database: journal mode and core schema" after 10200 ms`, no error. That test gives each of its three Runtimes a fresh folder, so the nervous child was the file's only opener and no lock was involved. The likely cause, plausible but not proven, is flush time: every start-up statement of the Store commits on its own (423 WAL frames for 194 pages), and at `synchronous=FULL` each commit waits for the disk. A loaded Windows runner pays a lot for each flush; B-118-T04 already turned flushes off for the test processes' own connections, but not for a Runtime's children. Measured on Tabgha (Windows, Node 24.22.2) with three processes writing and flushing 1 MiB in a loop: opening a fresh Store took 1.07–1.17 s, far short of the 30 s seen in CI; what stretches it there is unexplained (core schema 173–241 ms, migrations 357–487 ms; 156–183 ms idle; macOS 17 ms). Fix: the Store runs its start-up at `synchronous=NORMAL` (in WAL mode commits then do not wait for the disk and never corrupt; every start-up statement is idempotent or its own transaction, so a lost one reruns at the next start) and returns the connection's own setting once open, so the running coordinator keeps FULL. It lowers durability only once the switch to WAL has taken, since NORMAL outside WAL can corrupt on power loss (#767 review; test: "a fresh database is in WAL mode before…"). Residual risk: a power loss during start-up can lose the last start-up commits, including pending-approval delivery rows written then, so such a card may be delivered a second time after the restart. With it, the same load: 0.13–0.15 s; idle 45 ms. One outer transaction was rejected: the fleet migration refuses to run inside one. Test: `test/startup-watch.test.ts` ("starts up without a flush per statement"; the test commit failed before the fix).
