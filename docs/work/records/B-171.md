| **Issue** | Seen 2026-11-26 on NERV-02 (Tabgha, Windows): `nerv update` and `lifecycle-apply stop` are refused with "Service or runtime ownership is unknown or belongs elsewhere." and "The definition must exactly match this profile, source and Node." The data home's `nerv-service.vbs` (written 2026-11-18, Node path and source correct) differs from what the current release renders only in its first comment line: B-102-T01 (`932ade4c`) dropped "(F-037)" from it. The Windows `inspect()` (`src/node-lifecycle-windows.ts`) compared the launcher byte for byte, so the definition read `foreign` and no lifecycle action could follow (install needs it absent, the others owned). `authorizedStart` already ignored the comment line (`windowsLauncherMatches`, B-091); `inspect()` did not. Blocks [B-091-T02](B-091.md). Owner workaround meanwhile: `service uninstall`, then `service install` run with the nvm Node, which rewrites both files. |
| **Reproduce** | Install the Windows service, replace the launcher's first comment line with the earlier release's text, run `lifecycle-plan stop`: the plan is blocked with the ownership blocker. |
| **Check** | A launcher that differs only in its first comment line is `owned`, and a fenced stop and uninstall run with it in place; a launcher whose command differs stays `foreign`; the test committed failing first (B-171-T01) passes unchanged after B-171-T02. |
