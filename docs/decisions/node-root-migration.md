# Replacement-root preparation and trust migration (F-005-T03)

2026-11-10, baseline main `f0e9a29`. The owner explicitly requested migration and root-key regeneration after the existing encrypted root could not be unlocked. This supersedes the earlier pause/choice gate for **preparing a real replacement root**, not disposable test trust. The original root remains retained. No additional approval of that scope is required; entering a new passphrase and obtaining target access remain actual external prerequisites.

## Current boundary

Existing `key init` refuses overwriting a key; `kaji import` refuses a different pinned root. Retain those safeguards. `Registry.records()` reads one registry history without a root-generation selector; changing only `config.kaji.root` would leave incompatible old signed history in that store. Neither renaming/removing the encrypted key nor manually repinning config is a complete migration. Append-only history must not be deleted, triggers bypassed or old rows silently rewritten to make a new root fit.

Two bases are enrolled under the existing root, with one selected main base. The chosen isolated profile is not enrolled. Actual identities, addresses, roots and paths are private. Base private identities are independent of the root and remain on their existing hosts. The new public registry should re-enroll the two currently enrolled public identities at their reviewed addresses, retain the main-base choice and include the selected isolated test profile at its separate loopback Kaji address. Previously revoked identities are not automatically re-enrolled. No capabilities, seats, grants or remote execution are added by preparing that registry.

## Delivered private preparation

A mode-0700 private staging directory contains a mode-0600 reviewed migration manifest and original signed public-registry snapshot. A terminal wrapper uses secure `getpass` with an actual controlling-TTY check; warnings that could cause input echo are refused. It confirms the new passphrase twice, with at least 12 characters, and passes it only through the stdin of a local Node child. No prompt, passphrase, raw root/private key or machine-specific artifact enters the repository or chat. The new root's encrypted file remains on the coordinator, never in the public peer bundle.

Before asking for a secret and again before staging, the helper checks unchanged reviewed source, old pinned root/encrypted-key digest, existing registry digest/signatures, exact enrolled identities/main choice, isolated public identity and noncolliding IDs/keys/addresses. Symlink endpoints and existing staging directories are refused. It uses the existing `createRootKey`, `unlockRootKey`, `signRecord` and `verifyRecord` interfaces. It exclusively creates the staging directory and accepted marker, encrypted new key, new-root-signed public registry, original public-registry snapshot and a completed **staged-not-activated** receipt. All files are mode0600; directory mode0700. A partial staging failure retains its artifacts and must be inspected; rerunning over an existing directory is refused.

Read-only review does not request a secret. Generation requires the owner's local Terminal; no actual replacement root was generated by the agent. The prior live encrypted key, config, SQLite registry, private base keys, workers and service definitions are not modified. A successful stage is not a migrated base or an offline backup.

## Activation remains unimplemented

A supported per-base adapter must be delivered/reviewed before live activation. Required acceptance:

1. Bind the exact old/new public roots, full reviewed bundle, base identities and snapshot/backup digests; independently compare the new public fingerprint on each host. Explicit owner authorization replaces unavailable old-root signing authority for this recovery, never network discovery or trust on first use.
2. Establish controlled quiescence of each selected runtime and descendants, pending outboxes, worker leases/locks and uncertain effects. Preserve outstanding uncertainty; never replay physical work or infer stopped effects from a timeout. No unrequested system-service or login/linger changes.
3. Make a consistent recoverable private backup, including SQLite sidecars and configuration plus retained old encrypted key. Create an independent offline copy of the new encrypted root and safely retain its new passphrase. A same-disk stage is not that backup.
4. Introduce explicit root-generation-aware registry selection/storage that preserves the old signed history immutably and never treats old-root records as trusted under the new root. Retain business data, private base identities and operation receipts. Do not disable append-only triggers or clear registry tables. Schema/reader compatibility and old-to-new/rollback behavior need cross-boundary tests.
5. Use durable, fenced/digest-bound acceptance, progress and recovery. Config and registry/root selection must remain recoverable across crashes; merely editing config and starting a process is insufficient. No automatic downgrade, rollback or cleanup after ambiguous effects.
6. Transfer only the reviewed signed public bundle/root to Tabgha and the isolated profile; never distribute the encrypted root/private material or admin/provider secrets. Refuse an unrelated existing root without the explicit bound migration operation.
7. Activate/restart under the selected owner procedure, verify exact local root, registry identities/main choice and current source on each base; then verify cross-base authentication, registry synchronization, old-root rejection and one harmless explicitly approved capability. Mixed-root/partial migration and loss/reconnect must remain visible. A completed stage or a successful import alone does not prove this.

No usable literal Tabgha SSH alias was found in the local inventory; no remote host was contacted. Remote access/identity and actual device acceptance remain explicit prerequisites. New key generation alone cannot migrate or revoke the trust of that host.

## Alternatives and reconsideration

Retain old trust while diagnosing the original passphrase: previously attempted, still available as a separate owner path; no corruption diagnosis was proven. Disposable test trust: explicitly not selected by the migration request and would not solve existing-base pairing. Overwrite root/config or clear registry: rejected for incompatible signed history, data/trust loss and bypassed safeguards. Staging first is retained because it creates a concrete reviewed new key/bundle without making the existing two bases disagree mid-operation. Reconsider the adapter/storage choice when its crash/rollback tests and actual target access are available; this document does not claim an implemented activation mechanism.
