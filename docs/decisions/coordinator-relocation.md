# Coordinator relocation without split brain

**Status: proposed, 12 November 2026 (F-016-T01); revised, 14 November 2026 (F-016-T10).** The independent review of 13 November found four blocking issues and five should-fix issues ([first review](../reviews/2026-11-13-f016-relocation-review.md)). This revision answers all findings and passed an independent second fresh-context review with zero blocking issues ([second review](../reviews/2026-11-14-f016-relocation-review-2.md)); awaiting owner agreement before implementation begins (no code implements it yet). F-016-T03 (signed snapshot export/import and safe standby swap), F-016-T04 (incremental log shipping), F-016-T05 (coordinator epoch and fencing tokens), F-016-T06 (standby-acked lease renewal and effect-boundary expiry checks), F-016-T07 (owner-initiated relocation with restore and quarantine) and F-016-T08/T09 (partition, sleep, reconnect and two-device acceptance) build on it once agreed.

## Problem

NERV runs one logical coordinator (`main` in the Gehirn registry) on an always-on host, while enrolled worker bases execute bounded jobs over the signed worker channel ([runtime boundaries](runtime-boundaries.md), [worker protocol](worker-protocol.md)). Today `src/kaji.ts` selects `main` from the newest root-signed `kind: 'main'` registry record (`serial` order), `src/nervous-process.ts` starts `store.tick()` and `store.expire()` unconditionally on every host, `src/cli.ts` starts `Runtime.startResumer`, `Runtime.startOutbox` and `Runtime.closeInterrupted` unconditionally, `src/runtime.ts` (`chatOnce`) falls back locally when `main` is offline, and `src/store.ts`, `src/ledger.ts`, `src/kaji-link.ts` and `src/telegram.ts` assume one static local SQLite store never relocates.

Moving the logical coordinator to another enrolled base (for example from the mini PC to the Mac before travel, or from an asleep, partitioned or lost host to a standby) raises five split-brain, state-collision and replay hazards:

1. **Incomplete or context-only state**: copying Lilith memory or conversation text without the Central Dogma ledger, approval states, inbox `deliveries` rowid sequence, reminder schedules, watch/brief checkpoints, Telegram card/offset state and `kaji_outbox` / `worker_outbox_attempts` receipts would replay fired reminders, reset native and Telegram delivery cursors, drop pending approvals or re-run uncertain remote actions.
2. **Simultaneous authorities during partition or sleep**: a locally self-renewed lease or non-wall-clock timer check allows an online partitioned coordinator—or a waking laptop—to renew itself, fire reminders, send web push, issue coordinator ledger grants, run `startOutbox` / `startResumer`, accept coordinator Kaji/REST mutations or poll Telegram while another base is promoted.
3. **Per-base state collision and local cursor drift**: importing `main`'s `deliveries.rowid` values into a base's existing `nerv.sqlite` collides with non-main rows (or swapping `nerv.sqlite` naively discards the standby's own `worker_jobs` locks/receipts, `worker_approvals` join rows, `PRAGMA user_version` / `root_migration*` tables and heartbeat-learned `registry` records), while Telegram's `telegram-state.json` offset, `cards`, `messages` and `inbox` sequence are currently local and un-replicated.
4. **Unfenced in-flight requests, offline fallbacks and side channels**: delayed Kaji/worker frames reaching un-pushed or outbound-only workers within cross-host skew, `Runtime.chatOnce` offline local fallback, direct-SQLite coordinator CLI writes (`remind`, `tick`, `approve`, etc.), coordinator HTTP REST mutations (`src/server.ts`), coordinator Kaji handlers (`/kaji/chat`, `/kaji/relay`), peer handlers (`/kaji/decide`, `/kaji/approvals/pending`), web push (`Store.dispatchPushReminders`) and Telegram `poll()` / `local-fallback` sends could mutate state or emit external effects after cutover—while overly blunt gating on worker paths would break enrolled worker execution (`worker.run`, `/kaji/decide`, `WorkerJobs.waitingApprovals()`).
5. **Secret leakage or registry rollback**: copying raw `data/` files copies private keys (`base-key`, `key-of-nebuchadnezzar.enc`), bearer tokens, Telegram tokens, `seat-keys/` and `native-auth.sqlite`, while overwriting `registry` from an older snapshot discards newer root-signed `revoke` records already present on the standby.

## Decision

### 1. Agency state separation, exact inventory, cursor continuity and promotion swap (F-016-T03, F-016-T04)

#### Per-base state vs. coordinator state: kept separate

Per-base host state and replicated logical coordinator state are **kept separate** (never merged into a single mixed `deliveries` sequence and never left competing on non-main schedulers):

- Under F-016, coordinator loops (`src/nervous-process.ts` `store.tick()` and coordinator `store.expire()`, watch polling, brief generation, Instrumentality, `Store.dispatchPushReminders`, `Runtime.startOutbox`, `Runtime.startResumer`, `Runtime.closeInterrupted`, `Watch.interrupt`, coordinator replication shipping and Telegram continuity polling) run **only** on the base whose local `coordinator_state.replication_mode = 'active'`. (Worker-host `store.expire()` sweeps ONLY destination worker approvals via `workerJobs.waitingApprovals()`, while local scheduled database backup `src/snapshots.ts` `startSnapshots` stays per-host.)
- Non-main bases never run independent coordinator reminder/watch/brief ticks or silently fall back to local execution when `main` is offline (`Runtime.chatOnce` fails closed if `baseId !== main` or `replication_mode !== 'active'`); non-main agency requests relay exclusively through active `main` over signed Kaji RPC.
- While acting as an enrolled standby/worker, incoming snapshots and incremental replication batches from `main` write strictly into a **dedicated standby database** (`coordinator-standby.sqlite`), leaving the host's active `nerv.sqlite` (holding live base-local `worker_jobs` locks/receipts, `push_vapid`, `kaji_seen`, `registry` heartbeat syncs, etc.) separate so `main`'s `deliveries.rowid` values never collide with local rows.

#### Exact SQLite table and file inventory

Note: `src/` currently has no SQLite `state` table (`deliveries_v5` in `src/store.ts` is only a transient migration artifact; `kaji_runs` was migrated into `worker_jobs`). F-016 introduces a replicated singleton table `coordinator_state` (for coordinator epoch/fence/lease/cursor state) and a strictly base-local table `standby_lease_state` (for the standby's persisted ack history).

#### Cursor continuity and outbox quarantine model

- **Native inbox cursors (`Store.inboxPage(after, limit, afterId)`)**: `src/store.ts` and `src/server.ts` (`/api/inbox`) paginate `deliveries` using integer `rowid` (`after`) and UUID `id` (`afterId`). Importing `main`'s exact `deliveries.rowid` and `id` values into `coordinator-standby.sqlite` keeps native client `after` cursors continuous across relocation without skipping or replaying delivered items.
- **Telegram state (`telegram-state.json` + `coordinator_state`)**: `State` in `src/telegram.ts` holds `{ messages?: CardMessage[]; offset?: number; inbox?: { sequence: number; id?: string }; cards: string[]; brief?: { date: string; at: string } }`.
  - When reusing the single shared coordinator bot (`telegram-token` configured on both coordinator and designated standby for continuity): the active coordinator persists `telegram_offset`, `telegram_inbox_seq`, `telegram_inbox_id`, `telegram_cards_json`, `telegram_messages_json` and `telegram_brief_json` into `coordinator_state` (emitting replication batches) at `TelegramChannel`'s `save()` checkpoints, while checking `isActiveCoordinator(now)` right before Bot API HTTP requests and before committing cursor/state advances. During promotion, the new coordinator both hydrates `telegram-state.json` from `coordinator_state` and constructs/reloads `TelegramChannel`'s in-memory `this.state` from that hydrated state before starting `poll()` (so stale in-memory state never overwrites disk, and up to 20 pending approval cards/buttons are neither duplicated nor orphaned).
  - If an operator instead configures distinct per-base bots (`src/telegram.ts` second-bot setup): `telegram_offset`, `cards` and `messages` are token-specific, so replicated continuity applies only to shared-token takeover / `telegram_inbox_seq` / `telegram_inbox_id`; secondary non-main bots never run autonomous local reminders/briefs/inbox flushes or local coordinator mutations (`poll()`/`handle()` relay strictly to active `main` or fail closed).
- **Outbox attempt quarantine**: Incomplete outbound coordinator intents sit in `kaji_outbox` (`done IS NULL`), while actual dispatch attempts sit in `worker_outbox_attempts` (`id PRIMARY KEY, attempted TEXT NOT NULL`), pre-dispatch cancels in `worker_outbox_cancels`, legacy queue items in `worker_legacy_outbox`, and terminal outcomes in `worker_outbox_reconciliations`. On promotion to `coordinatorEpoch = E + 1`, quarantine finds every `kaji_outbox` row with `done IS NULL` that has a matching `worker_outbox_attempts` row and no terminal `worker_outbox_reconciliations` row (plus any incomplete `worker_legacy_outbox` rows) and marks them `uncertain` (`quarantined`) rather than re-sending them.

#### Snapshot shipping, incremental batches and safe standby promotion swap

- **Signed snapshot export and standby import (F-016-T03)**:
  - Active coordinator exports all replicated tables in one read transaction with canonical manifest `{ version, root, sourceBaseId, coordinatorEpoch, coordinatorFence, headSeq, exportedAt, tableCounts, sha256 }` signed by its `base-key`. Snapshot transport uses `MAX_BACKUP_BODY`-class limits (64 MB, matching `/kaji/backup` in `src/kaji-link.ts`) or chunked transfer rather than `KajiLink`'s default `256 KiB` `MAX_BODY` limit.
  - Standby verifies the pinned root, `sourceBaseId`'s active `main` record at `coordinatorEpoch`, schema compatibility ([node upgrades](node-upgrades.md)) and `sha256`; serial-merges `registry` / `registry_roots`; imports replicated tables into `coordinator-standby.sqlite`; and rebuilds `facts_fts` and `episodes_fts` locally.
- **Incremental log shipping (F-016-T04)**:
  - Each committed coordinator mutation transaction (and Telegram `save()` checkpoint) appends an ordered replication batch keyed by `(coordinatorEpoch, seq)` with `prevDigest` and `batchDigest` (excluding serial-merged `registry` updates and strictly base-local tables).
  - Batches ship to standby via `POST /kaji/replicate` with coordinator epoch and lease headers (using explicit `MAX_BACKUP_BODY`-class sizing or chunking for large batches). Sequence gaps or `prevDigest` mismatches fail with `need_resync` (`expectedSeq`), leaving `coordinator-standby.sqlite` at its last verified checkpoint until catch-up or fresh snapshot completes.
- **Atomic promotion sequence (preserving `nerv.sqlite` local tables, `user_version`, and worker locks)**:
  1. **Quiesce open handles & settle standby `worker_approvals`**: Close `/api/dashboard/stream` SSE clients, reject new local mutations, stop coordinator/standby background loops, and wait for in-flight `WorkerJobs` SQLite transactions to settle. While standby's `nerv.sqlite` is still open with its local `approvals` table:
     - Pre-settle undecided (`approvals.decision IS NULL`) standby `worker_approvals` cleanly via `decideCore(..., 'reject', ...)` + `workerJobs.finish(..., { outcome: 'reject', ... })`.
     - Persist the effective approval status (`persisted_decision` from `approvals.decision`) onto `worker_approvals` so already-`approve`d uncertain jobs remain marked `'approve'` after the local `approvals` rows stay behind in `nerv.pre-standby.sqlite`. (`WorkerJobs.waitingApprovals()` uses `LEFT JOIN approvals p ON p.id = a.approval_id`, returning `hasApproval: p.id IS NOT NULL` and `COALESCE(p.decision, a.persisted_decision)` as `decision`; `Store.expire()`, `Store.cancelWorker()`, and `Store.releaseWorker()` call `decideCore(...)` **only** when `pending.hasApproval && !pending.decision`, preserving `'approve'` uncertainty in `Store.expire()` without throwing `No approval with that ID.`.)
     - Close `Store` and stop `src/nervous-process.ts` under an explicit `serve`/`Runtime` swap-quiesce guard (so `src/cli.ts`'s `child.once('exit')` shutdown hook does not abort `serve` mid-promotion), leaving zero SQLite/WAL handles open on `nerv.sqlite` or `coordinator-standby.sqlite`.
  2. **WAL checkpoint**: Run `PRAGMA wal_checkpoint(TRUNCATE)` on both `nerv.sqlite` and `coordinator-standby.sqlite`.
  3. **Preserve `nerv.sqlite`-resident local tables & trust records into `coordinator-standby.sqlite`**: Inside one transaction on `coordinator-standby.sqlite` attaching standby's `nerv.sqlite` (`AS local_db`):
     - Copy/retain **only** the strictly base-local tables that live inside `nerv.sqlite`: `worker_sessions`, `worker_jobs`, `worker_approvals`, `worker_cancellations`, `worker_releases` (preserving worker receipts, locks and fencing history per [worker protocol](worker-protocol.md)), `standby_lease_state`, `push_vapid`, `push_subscriptions`, `model_usage`, `registry_seen`, `kaji_seen`, plus conditionally (when present in `local_db.sqlite_master`) all four `root_migration*` tables (`root_migrations`, `root_migration_resource`, `root_migration_clock`, `root_migration_recovery`). (`~/.nerv-lifecycle/journal.sqlite`, `~/.nerv-bootstrap/journal.sqlite` and `native-auth.sqlite` stay untouched at their own paths.)
     - Serial-merge `local_db.registry` and `local_db.registry_roots` monotonically by `serial` (so no heartbeat-learned `revoke` or `main` record is rolled back).
     - Set `PRAGMA user_version` to `MAX(local_db.user_version, standby.user_version)` (respecting `user_version >= 6` / `config.kaji.rootBinding === true` in `src/store.ts`).
  4. **Atomic file swap**: Archive prior `nerv.sqlite` to `nerv.pre-standby.sqlite` and atomically rename checkpointed `coordinator-standby.sqlite` -> `nerv.sqlite`.
  5. **Activation transaction & restart**: Open `Store` on promoted `nerv.sqlite`, run the atomic activation transaction (Section 4), hydrate `telegram-state.json` and `TelegramChannel` in-memory `this.state`, initialize the `E + 1` lease (standby-acked via `POST /kaji/lease/renew` if another enrolled non-revoked standby remains, or single-base self-armed lease per Section 2 if no other non-revoked standby remains), and restart `src/nervous-process.ts` and coordinator loops under `replication_mode = 'active'`.

### 2. Coordinator epoch and standby-acked lease renewal (F-016-T05, F-016-T06)

#### Naming reconciliation with the worker protocol

To avoid clashing with existing `worker_sessions.epoch` (per-WebSocket `worker.hello` session epoch) and `worker_jobs.fence` (destination worker-local monotonic lease lock sequence in `src/worker-jobs.ts`), coordinator leadership terms use distinct names across registry records, SQLite and headers:

- `coordinatorEpoch`: monotonic integer in root-signed `kind: 'main'` records (`>= 1`; legacy `main` records without the field read as `coordinatorEpoch: 0`), `coordinator_state.coordinator_epoch`, and header `X-Kaji-Coordinator-Epoch`. A `kind: 'main'` record is valid only when `next.serial > prev.serial && next.coordinatorEpoch > prev.coordinatorEpoch`. Only the owner holding `Key of Nebuchadnezzar` (or a replacement root activated via [root migration](node-root-migration.md)) can sign `main` and advance `coordinatorEpoch`.
- `coordinatorFence`: monotonic coordinator epoch-mutation/lease counter persisted in `coordinator_state.coordinator_fence`, sent in headers (`X-Kaji-Coordinator-Fence`) and coordinator worker frames, and persisted on destinations separately from `worker_jobs.fence` (`max_coordinator_epoch`, `max_coordinator_fence`). Ordered streams (`/kaji/replicate` `(coordinatorEpoch, seq)`, `/kaji/lease/renew` `leaseSeq`, and `WorkerLink` WebSocket `sequence`) enforce strict per-stream monotonicity without rejecting concurrent `agent: false` HTTP RPCs on minor intra-epoch arrival reordering.

#### Partition-safe lease renewal, monotonic standby wait and destination skew bound

Holding the latest `main` record is necessary but not sufficient to act. The coordinator also holds a bounded lease (`LEASE_TTL_MS = 60_000`, target renewal interval `LEASE_RENEW_MS = 15_000`, coordinator safety margin `LEASE_SAFETY_MARGIN_MS = 5_000`):

- **With an enrolled standby base (normal case)**:
  - The coordinator **never renews its lease purely from local clocks**. Before sending `POST /kaji/lease/renew`, the coordinator records its own `reqStartedWallMs = Date.now()` and `reqStartedMonoNs = process.hrtime.bigint()`.
  - The standby verifies the coordinator's `base-key` signature (within `KAJI_CLOCK_SKEW_MS`), verifies `from === main`, verifies `X-Kaji-Coordinator-Epoch === maxSeenCoordinatorEpoch` (and `>= standby_lease_state.standby_coordinator_epoch`), confirms the standby has not begun promoting to `E + 1`, persists `{ standby_coordinator_epoch: coordinatorEpoch, last_ack_seq, last_ack_wall_ms, process_boot_id }` into local table `standby_lease_state`, records `lastAckMonoNs = process.hrtime.bigint()` in standby memory, and returns a base-key-signed acknowledgement `{ standbyBaseId, coordinatorEpoch, ackSeq, headSeq, leaseTtlMs: LEASE_TTL_MS }`. (Note: `/kaji/lease/renew` intentionally does **not** require `Date.now() - KAJI_CLOCK_SKEW_MS <= X-Kaji-Lease-Expires-At` on the incoming renewal request, so initial `E + 1` lease acquisition and >175s sleep recovery succeed cleanly.)
  - On receiving the signed standby ack, the parent `serve` process persists `lease_issued_at = reqStartedWallMs` and `lease_expires_at = reqStartedWallMs + LEASE_TTL_MS - LEASE_SAFETY_MARGIN_MS` (`reqStartedWallMs + 55_000` ms) in SQLite `coordinator_state`, sets its own `leaseExpiresMonoNs`, and pushes `{ coordinatorEpoch, leaseIssuedAt: reqStartedWallMs, leaseExpiresAt, ttlRemainingMonoMs }` over local IPC into child `src/nervous-process.ts` so the child updates its in-memory `leaseExpiresMonoNs` alongside SQLite.
  - **Partition isolation**: If the coordinator cannot reach the standby (even while remaining connected to Telegram, the internet or local workers), `/kaji/lease/renew` fails; within 55 seconds of its last acked renewal start, the partitioned coordinator self-fences (`replication_mode = 'fenced'`) and halts all coordinator loops and effects.
- **Unplanned standby wait horizon (`65_000 ms` vs. `300_000 ms` for un-pushed / outbound-only destinations)**:
  - Because `reqStartedWallMs` precedes standby's ack receipt `lastAckMonoNs`, guaranteeing at least `2 * LEASE_SAFETY_MARGIN_MS` physical margin without needing cross-host wall-clock alignment between coordinator and standby, standby's **minimum monotonic wait** is `LEASE_TTL_MS + LEASE_SAFETY_MARGIN_MS` (`65_000` ms) on `process.hrtime.bigint() - lastAckMonoNs` (if the standby process restarted since `standby_lease_state.last_ack_wall_ms`, wait the full `LEASE_TTL_MS + LEASE_SAFETY_MARGIN_MS` on `hrtime` from current process start plus `Date.now() - last_ack_wall_ms >= LEASE_TTL_MS + LEASE_SAFETY_MARGIN_MS`).
  - **Un-pushed / outbound-only destinations & delayed-frame clock skew (`LEASE_TTL_MS + 2 * KAJI_CLOCK_SKEW_MS = 300_000 ms`)**: Per `src/kaji-auth.ts`, signed request timestamps allow `±KAJI_CLOCK_SKEW_MS` (`120_000` ms) skew between sender and receiver clocks (`2 * KAJI_CLOCK_SKEW_MS = 240_000` ms span). On a destination base that has **not** received `maxSeenCoordinatorEpoch = E + 1` (a partitioned peer or an **outbound-only `GET /kaji/worker` worker** with no inbound HTTP listener per [worker protocol](worker-protocol.md)), sender lead `+120_000` ms plus receiver slack `Date.now() - KAJI_CLOCK_SKEW_MS <= coordinatorLeaseExpiresAt` keeps epoch-`E` frames acceptable until up to `T_ack + 55_000 + 240_000 = T_ack + 295_000` ms (`<= LEASE_TTL_MS + 2 * KAJI_CLOCK_SKEW_MS = 300_000` ms). Accordingly:
    - **Fast unplanned promotion (`65_000` ms)**: permitted only when **every** enrolled unrevoked peer and worker base acknowledges `coordinatorEpoch = E + 1` pre-activation (via HTTP `POST /kaji/epoch-push` or active coordinator/standby WebSocket), so zero surviving destinations accept epoch `E`.
    - **Conservative unplanned promotion (`300_000` ms = `LEASE_TTL_MS + 2 * KAJI_CLOCK_SKEW_MS`)**: required on standby's monotonic clock whenever any enrolled unrevoked peer or outbound-only/offline worker has **not** acknowledged `E + 1` pre-activation (unless revoked first via root-signed `revoke`).
- **Without an enrolled standby base (or when relocating into a sole surviving base)**:
  - When no other enrolled non-revoked standby exists, `main` holds a self-armed single-base lease (`LEASE_TTL_MS = 60_000`, `LEASE_SAFETY_MARGIN_MS = 5_000` in `coordinator_state.lease_expires_at`, synced via IPC into `nervous-process.ts`) subject to identical synchronous wake/wall-clock checks.
  - Relocating away from a host when no standby holds ack history requires explicit owner action in `nerv kaji relocate`: root-signed `revoke` of the old `main` host pushed to reachable peers/workers, OR `--confirm-old-host-down` plus the conservative `LEASE_TTL_MS + 2 * KAJI_CLOCK_SKEW_MS` (`300_000` ms) wait if any unrevoked worker/peer might still see stale frames.

#### Sleep detection, effect-boundary rechecks and benign lease re-arm

- **Sleep behaviour (`hrtime` vs `Date.now()`)**: On macOS and Linux, `process.hrtime.bigint()` pauses while the machine sleeps whereas `Date.now()` advances; Node.js timer callbacks do not guarantee renewal/expiry runs ahead of an already-queued callback on wake.
- **Synchronous effect-boundary check `isActiveCoordinator(now)`**: Runs synchronously inside every coordinator effect boundary (in both `serve` and child `nervous-process.ts` inside SQLite transactions) and checks all four conditions:
  1. `coordinator_state.replication_mode === 'active'` and this base matches the newest verified `main` at `maxSeenCoordinatorEpoch`.
  2. `Date.now() < coordinator_state.lease_expires_at` (catches sleep and restarts unconditionally, even before any wake timer runs).
  3. In long-running `serve` and `nervous-process.ts` processes, `process.hrtime.bigint() < leaseExpiresMonoNs` (catches backward NTP wall-clock jumps while awake).
  4. Persisted `coordinator_state.coordinator_epoch` equals `maxSeenCoordinatorEpoch`.
- **Benign sleep wake (`nerv kaji lease-rearm`) vs. relocation**:
  - When active `main` sleeps (even longer than 175 seconds) and wakes with no relocation: if its enrolled standby is reachable and reports `maxSeenCoordinatorEpoch === E`, `serve` automatically calls `POST /kaji/lease/renew` signed with `main`'s **`base-key`** (neither the offline root key nor manual CLI intervention needed; `/kaji/lease/renew` does not reject an expired `X-Kaji-Lease-Expires-At`) and pushes the renewed lease over IPC to `nervous-process.ts`.
  - Only when no standby is enrolled or reachable on wake does resuming require explicit owner command `nerv kaji lease-rearm --confirm-sole-coordinator`, signed locally with the host's own **`base-key`** (NOT `key-of-nebuchadnezzar.enc`, since `main` identity and `coordinatorEpoch` are unchanged). When `serve` is running, `lease-rearm` calls an authenticated loopback HTTP endpoint on `serve` (`POST /api/kaji/lease/rearm` using `Authorization: Bearer <token>`, gated strictly on the file-backed `root` admin token matching `/api/stop`, keeping `/rpc` read-only) so `serve` refreshes SQLite + pushes `leaseExpiresMonoNs` over IPC to `nervous-process.ts`; when `serve` is stopped, it updates SQLite directly.

### 4. Owner-initiated relocation, lost-laptop recovery and restore (F-016-T07, F-016-T08, F-016-T09)

- **Explicit owner action only**: Missed heartbeats or `KajiLink` offline events never trigger automatic failover. Relocating `main` always requires an owner-signed registry update (`nerv kaji relocate`, signing `kind: 'main'` with `coordinatorEpoch = E + 1`).
- **Context copying alone never grants leadership**: A base cannot activate as coordinator for `coordinatorEpoch > 1` from an empty store or copied Lilith facts/chat logs alone. Activation requires a verified `coordinator-standby.sqlite` (`replication_mode = 'standby'`, verified `headSeq` and `stateDigest`) or an explicit owner-approved cold restore from a verified signed snapshot bound to `previousEpoch: E` and expected `minHeadSeq` / `snapshotDigest`.
- **Cutover protocol**:
  1. **Pre-activation epoch push**: Once `nerv kaji relocate` stages the root-signed `main` record (`coordinatorEpoch = E + 1`), push it to all reachable peers and workers (via `/kaji/epoch-push` and active WebSockets) so they persist `maxSeenCoordinatorEpoch = E + 1` and reject epoch `E` before `E + 1` opens effects.
  2. **Planned relocation (old coordinator reachable)**: Old coordinator stops schedulers (`draining`), halts new ticks/sorties/outbox/resumer/pushes/Telegram, flushes final batch `headSeq`, clears its SQLite lease (`lease_expires_at = 0`, `replication_mode = 'fenced'`), and returns a base-key-signed **drain receipt** `{ baseId, coordinatorEpoch: E, finalSeq, stateDigest, leaseRevokedAt }`. Standby executes Section 1's 5-step promotion swap, confirms reachable peers/workers hold `E + 1`, and activates `E + 1` immediately once all unrevoked destinations are accounted for (all unrevoked workers acked `E + 1`, or conservative wait / revoke applied).
  3. **Unplanned relocation (old coordinator asleep, partitioned or lost)**:
     - Standby refuses promotion until the Section 2 horizon passes on its own monotonic clock: `65_000` ms (`LEASE_TTL_MS + LEASE_SAFETY_MARGIN_MS`) since last `standby_lease_state` ack if every enrolled unrevoked peer/worker acknowledged `coordinatorEpoch = E + 1`, or `300_000` ms (`LEASE_TTL_MS + 2 * KAJI_CLOCK_SKEW_MS`) whenever any unrevoked peer or outbound-only/offline worker did not acknowledge `E + 1` (or when no standby ack history exists alongside `--confirm-old-host-down` / root-signed `revoke`).
- **Lost-laptop relocation**:
  - When a `main` laptop is lost or destroyed, recovery requires:
    1. Retrieving the **offline USB backup** of `key-of-nebuchadnezzar.enc` (recommended by `nerv key init` in `src/cli.ts`; snapshots never replicate it) and the owner's root passphrase.
    2. Using the offline root key to sign **both** a `kind: 'revoke'` registry record for the lost base and a new `kind: 'main'` record (`coordinatorEpoch = E + 1`) naming the replacement base, pushing/importing (`kaji import`) both records onto every surviving base.
    3. Applying the Section 2 wait horizon (`65_000` ms if all remaining unrevoked bases acked `E + 1`, else `300_000` ms), initializing a single-base self-armed lease on promotion if no other non-revoked standby remains in the mesh, and rotating exposed device secrets (`telegram-token`, `anthropic-key`, `token`).
    4. If `key-of-nebuchadnezzar.enc` itself was lost without an offline backup or its passphrase was exposed on the lost device, the owner must perform a **[replacement-root migration](node-root-migration.md)** before re-enrolling surviving bases.
- **Atomic activation and quarantine on the promoted coordinator**:
  - Inside one SQLite transaction in promoted `nerv.sqlite` (`coordinatorEpoch = E + 1`):
    1. Reconcile unfinished sorties/watches using exact `src/ledger.ts` and `src/watch.ts` statuses (`sorties.status` is `'open' | 'done' | 'failed' | 'revoked'`): call `Watch.interrupt()` on active `watch_runs` (`state = 'running'` -> `'interrupted'` and `ledger.spear()` -> `'revoked'`); call `Ledger.closeInterrupted` (`status = 'open'` -> `'failed'`) on unblocked interrupted Misato sorties (keeping pending `approvals.decision IS NULL` and unanswered `misato.asked` clarifications `'open'` for continuation under `E + 1`; any open `misato.waiting` sortie whose unconsumed epoch-`E` grant was revoked is safely closed/re-evaluated by `Runtime.startResumer` without reusing expired epoch-`E` grants).
    2. Revoke/expire all unconsumed coordinator `grants` (`used IS NULL AND revoked IS NULL`) from epoch `E`.
    3. Query incomplete `kaji_outbox` rows (`done IS NULL`) joined against `worker_outbox_attempts` lacking a terminal `worker_outbox_reconciliations` row (plus incomplete `worker_legacy_outbox` rows) and quarantine them as `uncertain` for manual owner reconciliation.
    4. Set `replication_mode = 'active'`, `coordinator_epoch = E + 1`, increment `coordinator_fence`, hydrate `telegram-state.json` and `TelegramChannel` in-memory `this.state` from `coordinator_state` (when using the continuity bot token), initialize the `E + 1` lease (standby-acked via `POST /kaji/lease/renew` if another enrolled non-revoked standby remains, or single-base self-armed lease if none), sync `leaseExpiresMonoNs` to `nervous-process.ts` over IPC, and restart coordinator background loops.
- **Reconnect of the old coordinator (F-016-T08, F-016-T09)**:
  - On wake or reconnect, `Date.now() < coordinator_state.lease_expires_at` already fences coordinator ticks, pushes, outbox/resumer work, coordinator REST/CLI writes, Kaji handlers and Telegram `poll()` / `local-fallback`. On first Kaji/registry sync or `kaji import`, it merges higher-serial `main`/`revoke` records, transitions permanently out of `active` into non-main standby/worker state, closes stale `/api/dashboard/stream` SSE clients, drops pre-cutover timers/coordinator grants, and can later re-seed a fresh `coordinator-standby.sqlite` if enrolled and unrevoked.

## Alternatives rejected

| Alternative | Why not |
|---|---|
| Automatic Raft / Paxos consensus and heartbeat-triggered leader election | Violates [runtime boundaries](runtime-boundaries.md): NERV runs two or three bases across home LAN, Tailscale and sleeping laptops, where quorum loss and sleep would cause spurious failovers or halt solo operation. |
| Self-renewed coordinator lease using local clocks only | Vulnerable to split brain when old `main` is partitioned from standby yet reachable by Telegram, web push, workers or CLI. Standby-acked renewal plus monotonic wait prevents two active coordinators. |
| Merging or naively swapping `nerv.sqlite`, or copying external `.sqlite` files in SQL | Merging `deliveries.rowid` breaks `/api/inbox?after=` cursors; naively swapping `nerv.sqlite` over deletes `worker_jobs` receipts, breaks `worker_approvals` INNER JOIN `approvals`, drops `root_migration*`/`user_version` or rolls back `registry`; attaching external `~/.nerv-lifecycle`/`~/.nerv-bootstrap` journals inside `nerv.sqlite` fails (`no such table`). The 5-step quiesce-merge-swap preserves every layer cleanly. |
| Unconditional `isActiveCoordinator(now)` inside `Ledger.authorize`, `/api/models*`, or `kaji import` | Breaks legitimate F-014 worker `worker.run` / `/kaji/decide` execution, blocks host-local model/pilot/update routes, and prevents `kaji import` trust bootstrap/recovery. Scoping fencing by authority mode avoids both split brain and false lockouts. |
| Leaving `Runtime.chatOnce` offline local fallback or non-main shared-bot `TelegramChannel.poll()` enabled | Allows a partitioned standby/worker to run forked local sorties or steal Telegram updates (`409 Conflict`). |
| Context-only takeover or raw `nerv.sqlite` / `data/` file sync | Drops ledger/approval/attempt uncertainty state or leaks private keys (`base-key`, `key-of-nebuchadnezzar.enc`, `seat-keys/`), tokens, `config.json`/`scrolls.json` host policy and `kaji_seen`. |
| Automatically replaying incomplete `kaji_outbox` + `worker_outbox_attempts` rows | Attempted remote jobs may already have run on workers; quarantining as `uncertain` matches [worker protocol](worker-protocol.md). |
